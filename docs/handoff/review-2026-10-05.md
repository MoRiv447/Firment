## Part 2 — confirmed defects

All are the same shape: **the fix exists, and one copy of the thing it fixes was missed.**

### 1. The workbench self-heal guards the target session and not the siblings it rewrites — medium

`gui/src-tauri/src/workbench.rs:140-142` refuses the one-time tag self-heal only when the
**registered mainline** has a turn running:

```rust
if needs_heal && !crate::commands::is_session_running(&shared, &cfg.mainline_session) {
    let _ = store.mark_mainline(&cfg.mainline_session);
}
```

But `mark_mainline` (`crates/firment-core/src/session.rs:705-714`) demotes **every** other
Mainline session sharing that cwd, and saves each one (`:710`). The sibling command
`workbench_set_mainline` already got this right — `workbench.rs:170-181` collects
`mainline_siblings(&session_id)` plus the target and refuses if **any** of them is live, with a
comment naming the hazard ("a turn still running in the session that currently HOLDS the role
had its transcript saved by this demotion with nobody in front of it asked").

**Trigger.** A sibling Mainline session on the same cwd is mid-turn while someone opens the
Workbench tab and the tags happen to be wrong (`needs_heal`). The demotion's `save` is a whole
transcript write. If it lands after that turn's own final `store.save(&self.session)`, the
turn's file is replaced by the pre-turn content the demotion loaded — the turn's messages are
gone, and neither side reports anything.

**Why the gates missed it.** The transcript-guard gate never opens `workbench.rs` (above), and
the workbench-file gate only counts `.save(` on `workbench.toml`. Both were run.

### 2. `config.toml` is written non-atomically in two places — medium

`session::write_atomic` exists (`crates/firment-core/src/session.rs:911`) and is used by
`edit_file`, `write_file`, `todo`, `flash`, `rename_symbol` (twice), `gui workbench.rs:695`,
and — explicitly, with the reason written down — by `save_auth_at`:

```
config.rs:1465  crate::session::write_atomic(path, &serde_json::to_string_pretty(auth)?)?;
```

The comment there records why: *"the old `fs::write` truncated the store before filling it
back in, so a crash … left an empty or half-written `auth.json`."* The user's config did not
get the same treatment, in either of its two write sites:

- `config.rs:1063` — `Config::save`, `fs::write(path, text)?`. This is the door every
  settings write uses, including the GUI's (`commands.rs:578`, `:851`).
- `config.rs:1093` — `load_or_create`'s deprecated-DeepSeek-name migration, also bare
  `fs::write`. This one is worse than the first: it fires on a plain **read**, so merely
  starting a `firm` built after 2026-07-24 against an older config rewrites that file.

**Consequence.** Truncate-then-write, so an interruption between the two leaves `config.toml`
empty or half-written. The next load fails to parse it (`Config::load` → `ConfigError`), and
the user's providers, keys-by-reference, budgets and tool settings are gone with no backup.

**On the record's scope.** `review-2026-10-03.md` accepts "`Config::save` rewrites
`config.toml` without preserving comments". That accepts **comment loss**. It does not accept
data loss, and the same repo's `auth.json` fix shows the team already treats this exact
truncation window as a real risk. This is not a re-report of the accepted item; it is the part
of the same function that item does not cover.

### 3. `max_subagent_depth` reopens the round-five `#25` class — medium

`#25` closed as: project config may only **tighten** cost ceilings. The policy is now stated
in the code, `crates/firment-core/src/config.rs:940-945`:

```
// Cost ceilings are TIGHTEN-only, the same rule the LA caps above apply with `.min()`: a
// checkout may ask for a smaller answer, a shallower budget, fewer calls per turn. It may
// not raise any of them, because `max_iterations = 100000` in a cloned repo is not a
// preference but a bill …
```

The three fields under that comment do use `.min()` — `max_output_tokens` (`:946-952`),
`max_iterations` (`:956-958`), `context_budget_chars` (`:962-966`). **`max_subagent_depth` is
merged fifty lines above the comment, at `:888-889`, and is a plain assignment:**

```rust
if project.tools.max_subagent_depth != default_max_subagent_depth() {
    config.tools.max_subagent_depth = project.tools.max_subagent_depth;
}
```

`max_subagent_depth` *is* a cost ceiling — it is the recursion limit for the `task` subagent
tool (`agent.rs:106`, default 2, `config.rs:571-572`). The only clamp anywhere on it is a
**floor**, `depth.max(1)` (`agent.rs:752`); no upper bound exists. So a cloned repo whose
`.firment.toml` says `max_subagent_depth = 999` gets it, and the agent can fan out a subagent
tree bounded by nothing but the iteration budget — the "not a preference but a bill" case the
comment is about. Being outside the `if` chain the fix touched is, as far as the tree shows,
why it was missed.

*(Adjacent, and deliberately not reported as a defect: `thinking` is also a plain assignment at
`:959-960`. It sits with the timeout knobs in the "availability, not trust" bucket — it cannot
grant itself a tool — so raising the user's thinking level is a cost the same comment's
exception seems to intend. Worth a decision, not a bug report.)*

### 4. `run_ctags` has a timeout and no output ceiling — medium-low

`crates/firment-tools/src/tools/symbols.rs:334-371` spawns `ctags -R` and drains its stdout in
a thread with `read_to_end` into an unbounded `Vec<u8>`. It has the 60 s deadline and kills the
child on expiry (`:356-367`), and its comment shows the author thought carefully about the
pipe — "a big tree overflows the OS pipe buffer (~64 KB) … every symbol lookup on that tree
silently degraded to the regex fallback". What it never got is the other half of the house
rule: `run_command` caps at `CAPTURE_CAP_BYTES` (`tools/util.rs`), `monitor.rs:257` and
`redteam.rs:324` cap at the same 8 MiB, and round five added a ceiling to the plugin path
(`#24`). `symbols` reaches the same OS with no ceiling at all.

**Consequence.** On a large repository, one symbol lookup buffers the whole ctags JSON in
memory — hundreds of MB bounded only by the 60 s deadline. The degradation is memory, not
correctness.

### 5. `redteam.rs` is the one serial read point still decoding per chunk — low

`crates/firment-tools/src/tools/redteam.rs:353/375/377`: `tail` is a `String`, and each read
does `String::from_utf8_lossy(&buf[..n])` then `format!("{tail}{chunk}")`. Of the five places
that read a serial port, the other four use `utf8::LineSplitter`
(`monitor.rs:231`, `hil.rs:2106`, `firment-cli/src/main.rs:2404`, `gui/src-tauri/src/hardware.rs:83`).
`read_window` is the fifth and the only one left. Its own comment says the chunk is "glued to
the tail of what was kept" so a marker split across reads is still seen — which is true for
ASCII only. A multi-byte needle (`oracle.extra_fault_signatures`, a non-ASCII
`heartbeat_regex`) straddling a 4096-byte read boundary becomes `U+FFFD` + `U+FFFD` and stops
matching *in the loop*.

**Correction, made while fixing it: this was first written here as "the case is then scored
alive", and that is wrong.** The verdict is not decided in the loop. `run_suite_with`
(`tools/redteam.rs:792`) calls `oracle::classify(&cap.text, saw_traffic, cap.timed_out, ..)`,
and `cap.text` is decoded once from the raw bytes (`:436`) — so a signature broken in half
classified correctly all along, and no case was ever mis-scored this way. What the split
actually cost was the **early exit**: the loop is meant to leave the instant a fault scene
appears (they are ephemeral) or a heartbeat arms `HEARTBEAT_TAIL_MS`, and a split signature or
a split multi-byte heartbeat left it reading to the full window instead. A latency defect, not
a correctness one — and the fifth copy of a rule its four siblings already agreed on.

## What this round says about its own exit criterion

Rounds four and five both set "a fresh audit finds nothing severe" and both failed it, and the
diagnosis written down was the right one: *a fix that lands on one copy is a finding waiting
for the next audit*. This round was asked to test that diagnosis directly, and it holds in both
directions — twelve of thirteen backlog items and nineteen of twenty round-four findings really
are closed, and the new defects are their siblings. The gates built in round four are real
instruments (each reads a file it does not write, each has a floor), but two of this round's
findings live in a hole all seven share: **every gate's scan target is a fixed list of files
and a literal string**. A rule enforced by reading one file for one spelling only covers the
copies that file happens to hold.

Two things follow, stated as the round's own output rather than as a plan:

- The six one-copy misses are each a two-line change (`.min()`, `write_atomic`, a sibling
  guard, a byte ceiling, `LineSplitter`, `unwrap_or_else`) — but the durable fix is to make the
  rule un-forgettable, which for `Config::save` means the atomically-written file set should be
  named once, and for the transcript guard means scanning the workspace rather than
  `include_str!("commands.rs")`.
- Nothing here is worth much until `origin/main` and a tag carry it. The gap in Part 4 is
  larger than any single item in Part 2.

### Findings

**1. A TOML typo in `rules.toml` stops the collector, not just the classifier — medium.**
`sbc-guard/guardd.py:78` parses the rules file with `tomllib.loads(path.read_text())` outside any
`try`. `compile_rules` (`:81-99`) is careful per rule — its own comment says a bad rule "must skip
THAT rule, not crash the daemon on startup and leave the board unwatched" — but a *syntax* error is
not a bad rule, it is a bad file, and it reaches `Guard.__init__` (`:110`) uncaught and then
`__main__` (`:340`). With `Restart=always` / `RestartSec=5` (`sbc-guard/sbc-guard.service`) the
process restarts every five seconds forever; systemd's default start limit (5 in 10 s) is not
reached at that cadence. **Nothing is subscribed during a restart loop**, so this is not "alerts
arrive late": the data plane documented as "append EVERY frame, never drop" (`:5`) receives no frame
at all. The built-in defaults already exist for the missing-file case (`:71`) — they are simply not
used for the unreadable-file case.

**2. An unbounded work queue whose single worker can take six minutes per item — low-medium.**
`guardd.py:117` builds `queue.Queue()` with no bound, `:201` queues the **whole** frame (clipped
only at publish time, `:268`), and `:118` starts exactly one worker. `classify` allows 2 × 180 s
(`:165`, `:176`). A device in a match storm therefore enqueues faster than the worker drains, and
the queue grows until the unit's `MemoryMax=256M` kills the process, which `Restart=always` then
restarts. Stated precisely: the RAW alert is published before the queue is touched (`:197`), so
alerting is not what breaks — what backs up is the LLM refinement and what dies is the process.
Every sibling on the Rust side carries a ceiling for exactly this reason; this is the one collector
without one.

**3. The retention pass never covers the corpus — low.** `guardd.py:374` globs `events-*.jsonl` and
deletes older than seven days, and the comment at `:372` calls those "daily sinks". `record_pair`
(`:250-253`) writes `pairs/<YYYYMMDD>.jsonl` — also one file per day — and nothing removes it. On
an SBC that is unbounded disk growth from a pass that reads as if it covered the directory.

**4. `install.sh` puts the binary on PATH without the replace the Rust path uses — low.**
`install.sh:85` is `install -m 755 "$BIN" "$INSTALL_DIR/firm"`: the target is written in place, so
an interrupted install leaves a truncated `firm` where a working one was. `firm update` is not
shaped that way — `crates/firment-cli/src/install.rs:211 replace_file` copies to
`<parent>/.firm.update.<pid>.tmp` and then replaces, on Windows through `MoveFileExW` with
`MOVEFILE_WRITE_THROUGH`. One guarantee, two installers, one of them without it. What keeps this
low rather than medium is that the checksum *is* mandatory (`:70-73` abort when SHA256SUMS is
missing or has no row for the asset) — that was the part that used to install unverified.

**5. Three leftover experiment scripts ship inside `sbc-guard/` — low.** `think_ab.sh`,
`effort_test.sh`, `effort_test2.sh` POST to `openrouter.ai` for a model called `stealth/ox-alpha`.
Nothing to do with the guard, and `sbc-guard/README.md` never mentions them. They also teach the
wrong habit with a key: two take it as `$1` (visible in `ps` and shell history) and the third reads
`/tmp/key.txt`, world-readable by default.

**6. `guardd.py:33` `DATA_DIR` is dead and names a different directory than the live default —

`config.toml`'s `data_dir`, whose default is `~/sbc-guard-data` (`:39`). Two names for the data
directory, one of them wrong, is the shape of the next reader's mistake.

### The two fixes, as landed

Both in `sbc-guard/guardd.py`, plus the unit, the shipped config and the README. The data plane's
promise ("append EVERY frame, never drop") is why these are worth more than their severity
suggests: every second spent in a restart loop is a second with no MQTT subscription, so the loss
is the collector, not just the alerts.

**A broken `rules.toml` degrades instead of killing the daemon.** `load_rules` catches
`TOMLDecodeError`/`OSError`, prints the reason, and returns `DEFAULT_RULES` — hoisted to a module
constant so the missing-file and unreadable-file paths cannot drift into two different rule sets.
It also speaks up when the file parses but declares nothing, because a misspelled `[[rules]]`
table yields an empty list: a guard that escalates nothing while looking healthy.

**A broken `config.toml` exits 2 instead of looping.** Falling back to the defaults is wrong here
— the default broker is `127.0.0.1`, so a guard the operator pointed at another host would
silently watch the wrong one. The unit gained `RestartPreventExitStatus=2`, so systemd records a
failure that `systemctl status` shows instead of restarting every five seconds forever. The two
files are deliberately held differently, and the README now says which is which and why.

**The refinement queue is bounded, and its losses are counted.** `[guard] queue_max` (default 256)
sizes `queue.Queue`; a full queue drops the newest refinement request via `put_nowait` rather than
blocking paho's callback thread — blocking it is the same sin the file already refuses to commit
with classification — and bumps `llm_dropped`. `[ollama] timeout_s` (default 60, replacing a
hard-coded 180) is the knob that sets the worst case one item can hold the single worker, 2 ×
timeout, which is the number `queue_max` has to absorb. The heartbeat carries `queue_depth`,
`queue_max` and the counter, so shedding is visible rather than implied.

**Verified by running it, not by reading it.** `sbc-guard/test_guardd.py` (added; standard library
only, no pytest) runs `guardd.py` as a real subprocess with stub `paho`/`requests` modules in a
temp tree and asserts four cases. Output on this machine:

```
PASS  A rules.toml broken -> warn + built-in rules + stays up   (exit=124)
PASS  B config.toml broken -> exit 2 + reason on stderr         (exit=2)
PASS  C both fine -> reaches [guard] up                         (exit=124)
PASS  D misspelled [[rules]] -> says nothing will escalate      (exit=124)
4/4 cases passed
```

`exit=124` is the case deadline killing a process that was still up, which is the assertion for A,
C and D; B is asserted on the code the unit refuses to restart on. This is the first test
`sbc-guard/` has ever had. There is still no CI step that runs Python (`ci.yml` does not look at
it at all) — recorded as a decision to make, not as an oversight: the README says how to run it by
hand.

### The other four, as landed

**`pairs/` is reported instead of expired.** `Guard.gc()` is a method now, holding both policies
next to their reasons: the raw event sinks keep their seven-day window, and the fine-tuning corpus
is kept until an operator asks otherwise (`[guard] pairs_keep_days`, default 0 = keep forever).
Expiring a corpus on a timer would throw away the thing it exists to accumulate, so the repair for
unbounded growth is visibility rather than deletion — the heartbeat carries `pairs_files` and
`pairs_bytes`. What the comment used to get wrong ("daily sinks", plural, as though the directory
were covered) is now named exactly.

**`install.sh` stages and renames.** `install` writes its target in place, so an interruption left a
truncated `firm` on PATH. The binary now goes to `$INSTALL_DIR/.firm.new.$$` and `mv -f`'d into
place — a same-filesystem rename, the same guarantee `firm update` gets from `replace_file`. A
rename also replaces a binary that is currently running, where writing in place gets ETXTBSY. The
EXIT trap was widened so an interrupt cannot leave the staging file behind either.

**The three probe scripts stop teaching the wrong key habit.** They are not part of the guard —
they POST to OpenRouter for a model called `stealth/ox-alpha`, and their conclusions are what the
`config.toml` notes about thinking models record — so they are kept, with a header saying so. The
key now comes from `$OPENROUTER_KEY` (`:?` refuses before any request) instead of `$1`, which
landed in shell history and in `ps`; the response body goes to a `mktemp` file under an EXIT trap
instead of a fixed `/tmp/rr.json` any local user can pre-create; and `effort_test2.sh` no longer
reads `/tmp/key.txt`.

**`guardd.py`'s dead `DATA_DIR` is gone.** It named `~/sbc-guard` — the *code* directory — while
the sink directory comes from `data_dir` (`~/sbc-guard-data`). Two names for the data directory,
one of them wrong, is the shape of the next reader's mistake.

**Verified by running, again.** Three harnesses, all passing:

```
guardd.py failure paths   sbc-guard/test_guardd.py                          4/4   (in the repo)
install.sh end to end     local http mirror + uname/find/mktemp shims      10/10  (one-off)
the three probe scripts   curl/sleep/python3/mktemp shims                    7/7   (one-off)
```

The install run covers a clean install, the installed binary executing, no staging file left
behind, exactly one PATH line (and still one after a re-run), and a bad checksum refusing while the
previously working binary keeps working. The probe run covers the refusal firing before any
request, and the body being parsed from a `mktemp` path rather than a fixed one.

Two notes worth keeping, because each cost a round of debugging and neither is a defect in the
code: on this host `find` resolves to `C:\Windows\System32\find.exe` (no `-type` flag), and MSYS
`mktemp` returns `/tmp/...`, which native Windows programs cannot open — so the install and probe
harnesses need `uname`, `find` and `mktemp` shims to measure the script instead of the host. Neither
applies to the platforms these scripts target, and `install.sh` refuses a MINGW host outright. The
install and probe harnesses are deliberately **not** committed: they are Windows-shaped workarounds
I cannot run as-committed, and a test that passes only with local shims is worse than a stated gap.
`install.sh` therefore still has no test in the repository.
