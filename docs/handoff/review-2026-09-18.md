## Findings — fixed

### 1. The estimate ledger deduplicated on `seq` alone

`recordCompleted` kept a module-level `Set<seq>` so re-renders could not inflate the
samples. But `seq` is the **agent's own counter and restarts at 1 with every agent** —
so from the second session on, every finished run looked like one already counted, the
ledger stopped learning, and the `~4.0s` estimate would never appear again. Found by
reading the counter's origin (`Agent.tool_seq`, initialised per `Agent::new`), not by a
test failing; the fix carries a regression test that runs two sessions through the same
seq range and asserts four samples.

Two things the fix's first draft got wrong, both caught by the existing tests rather
than by reasoning:

- A **high-water mark** instead of a set is wrong: `seq` is per tool *start* and
  concurrent tool calls finish out of order, so a card that started earlier but finished
  later is skipped for good — a silently missing sample. The failing assertion
  (`expected 47000 to be 4200`) is the median of the two samples that survived.
- The ledger's `runs` map is **not** per session. How long `flash` takes is a property
  of the tool and the board; a session boundary does not change it.

### 2. The serial reconnect budget was per capture

Three reopen attempts, spent over the whole capture: a cable replugged four times loses
the fourth to a budget the first three spent — the capture failing at the thing it is
for. Now a stretch that **delivered lines** is evidence the port works and resets the
budget; a stretch that delivered nothing does not, because a port that opens and dies
instantly is exactly what the budget is for. Two tests pin both sides: five replugs keep
capturing, and a port that never delivers still gives up.

### 3. A gap marker glued itself to the resumed capture

`note()` only opened a newline before the marker; the chunk that follows it is a
`lines.join("\n")` with no trailing newline, so the resumed capture's first line landed
on the marker's line — and the timeline test caught it, because that line no longer
began with its timestamp. Markers are now complete lines.

## Findings — recorded, not fixed

- **The rail width has no justification anywhere.** 248px in `App.module.css`; the plan
  asked for 200–205 against a pre-rewrite rail near 160. Recorded as an open question in
  `docs/design/layout.md` rather than narrowed to match a stale plan.
- **A retry after a partially applied turn re-asks with the tree as the failed turn left
  it.** `Session::retry_last` rewinds the transcript, not the working tree; the journal
  and `/undo` are separate. Probably right, but it is a decision the plan should make,
  not one to slip into a fix.
- **The reconnect covers `monitor.rs` and the CLI only.** `hil.rs` (two sites),
  `redteam.rs`, `hardware.rs` (GUI) and the baud probe each open their own port, and
  their lifetimes differ enough that each needs its own judgement.
- **The advisory gate has never run.** `ci.yml`'s `audit` job is written and this
  machine cannot execute it (no network — measured); its first run on a runner is the
  first time anyone sees the advisory list.

## Update — later the same day

The reconnect now covers the **HIL capture loop** too (`hil.rs`), spending the same
budget through the same `open_port`, with the same reset rule (a stretch that delivered
lines is a new outage). The HIL loop is wired inline like the CLI's and is not directly
tested — no fake reader exists in that file — so what is tested is the policy it spends
(`monitor.rs`'s four reconnect tests), and the wiring is the mechanical part.

Three sites are judged **not** to want it, and the reasons are part of the decision
rather than leftovers: `redteam.rs` has its own `Executor`/`TargetLink` model with an
explicit recovery phase; `gui/src-tauri/src/hardware.rs` would need the write handle
re-cloned and a frontend notification designed (a separate step); and the baud probe is
a 50ms best-effort probe whose outer loop already retries per rate.
